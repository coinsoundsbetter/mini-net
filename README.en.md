---

- **Define network objects in C#.** Compose replicated components with `GhostBuilder`. No Unity prefab setup is required.
- **Drive the network loop yourself.** Call `TickIncoming()` to process incoming traffic, run your game logic, then call `TickOutgoing()` to collect and send state changes.
- **Test in a standalone .NET process.** The runtime runs independently of Unity. Developers and coding agents can configure both endpoints in code, drive the loop, and assert on the results.

## Features

| Feature | What you can do |
| --- | --- |
| Connections | Listen for clients, disconnect a specific player, or connect and disconnect as a client. Both endpoints expose connection and error events. |
| Messaging | Register handlers for typed messages or send raw bytes. Choose reliable or unreliable delivery. |
| Object replication | Define a network object (a Ghost) with a template. Spawn, update, and despawn it on the server. Clients receive its initial state followed by changes. |
| Field replication | Mark fields with `[GhostField]`. The Weaver generates serialization and change detection code at compile time. Clients can subscribe to spawn, update, and despawn events. |
| Visibility and child objects | Filter recipients by connection. A child Ghost inherits its parent's visibility and can restrict its audience further. |
| Ownership | Assign or transfer ownership and check whether the sender owns an object before acting on a request. |

## Quick start

These examples share a server and a client and use the `MiniNet` and `MiniNet.Replicate` namespaces.

> [!NOTE]
> The typed messages and replicated fields below use serialization code generated by the **Weaver** during Unity compilation. When compiling MiniNet from source in a standalone .NET project, register message readers and writers and implement component serialization. [Compilation and serialization (Chinese)](Assets/MiniNet/README.md#编译与序列化)

### 1. Start both endpoints and log the connection

For a local demo, create both endpoints in one process. Subscribe to events before listening or connecting. Register the handlers and templates in the later examples before processing incoming traffic.

```csharp
var server = new Server(new TransportServer());
var client = new Client(new TransportClient());

server.RemoteClientConnected += id => System.Console.WriteLine($"Player {id} connected to the server");
client.OnConnected += () => System.Console.WriteLine("Client connected to the server");

server.Listen(7777);
client.Connect("127.0.0.1", 7777);
```

Run the following in the host's update loop. Each endpoint logs a message when the connection opens. When running in separate processes, each host drives its own endpoint.

```csharp
server.TickIncoming();
client.TickIncoming();
// Run game logic for this tick.
server.TickOutgoing();
client.TickOutgoing();
```

On exit, call `client.Disconnect()` and `server.Shutdown()`.

### 2. Send a message and reply to the client

Both endpoints share the message type. The server handler receives the sender's connection ID, so it can reply directly to that client.

```csharp
public struct ChatMessage : INetworkMessage {
    public string Text;
}
```

```csharp
server.RegisterHandler<ChatMessage>((sender, msg, mode) => {
    System.Console.WriteLine($"Player {sender} says {msg.Text}");
    server.Send(sender, new ChatMessage { Text = "Received: " + msg.Text });
});

client.RegisterHandler<ChatMessage>((msg, mode) => System.Console.WriteLine(msg.Text));
client.OnConnected += () => client.Send(new ChatMessage { Text = "Hello" });
```

Keep the loop from example 1 running. The client prints `Received: Hello`.

### 3. Change health on the server and replicate it automatically

Store health in a `GhostComponent` and mark the field with `[GhostField]`. Use the same template ID and component order on both endpoints.

```csharp
public sealed class PlayerState : GhostComponent {
    [GhostField] public int Hp;
}
```

```csharp
var playerTemplate = new GhostBuilder(1).Component<PlayerState>().Build();
client.ReplicateManager.RegisterTemplate(playerTemplate);

void LogHp(Ghost ghost) {
    if (ghost.TryGetComponent<PlayerState>(out var state))
        System.Console.WriteLine($"Player {ghost.NetId} has {state.Hp} HP");
}
client.ReplicateManager.Spawned += LogHp;
client.ReplicateManager.Updated += LogHp;

var player = server.ReplicateManager.Spawn(playerTemplate);
player.GetComponent<PlayerState>().Hp = 100;
```

The client logs 100 HP when the player first appears. Later, apply damage on the server:

```csharp
player.GetComponent<PlayerState>().Hp -= 10;
```

The next server `TickOutgoing()` picks up the change. The client logs 90 HP when it processes the update. No separate damage message is required.

### 4. Show the player to everyone and the tactical target only to teammates

Keep the player template from example 3. Put the tactical target on a child Ghost so the server can choose who receives it.

```csharp
public sealed class TeamTactics : GhostComponent {
    [GhostField] public int TargetId;
}
```

```csharp
var tacticsTemplate = new GhostBuilder(2).Component<TeamTactics>().Build();
client.ReplicateManager.RegisterTemplate(tacticsTemplate); // On every client, before receiving.

var teammates = new System.Collections.Generic.HashSet<int>();
var tactics = server.ReplicateManager.SpawnChild(player, tacticsTemplate,
    visibleTo: teammates.Contains);
tactics.GetComponent<TeamTactics>().TargetId = 42;
```

Update the set on the server when a player joins or leaves the team. Use the player's `connectionId` from the connection event.

```csharp
teammates.Add(connectionId);    // Next sync: send the child and its current target.
// Later, when the player leaves the team:
teammates.Remove(connectionId); // Next sync: remove the child from that client.
```

A client must see the parent and pass the child's `visibleTo` filter to receive the child. Players outside the team can still see the parent's health. Sending the tactical target and its updates only to teammates saves downstream bandwidth. [Two-client visibility test](Assets/MiniNet/Tests/GhostBindingTests.cs)

## How MiniNet compares with Mirror

Both frameworks can replicate player health and share a tactical target with teammates. The practical differences are how you define the player, who drives the network loop, and where you express the visibility rule.

| Integration question | MiniNet | Mirror |
| --- | --- | --- |
| How do I organize client and server code? | MiniNet has no central `NetworkManager`. The application configures `Client` and `Server` separately. MiniNet encourages keeping gameplay code separate from the start and sharing message and state definitions. | `NetworkManager` provides entry points and lifecycle callbacks for client, server, and host modes. Projects can also organize gameplay code separately for each endpoint. |
| Where can I run and test it? | Create both endpoints and test their interactions in a standalone .NET process. When compiling from source, supply serializers for typed messages and replicated components. | Network identities and behaviours are Unity `MonoBehaviour` components. End-to-end tests typically exercise them in a Unity environment. |
| How do I define a player with health? | Add a component with a `[GhostField]` to a `GhostBuilder` template and spawn it from code. No prefab setup is required. | Give a GameObject a `NetworkIdentity` and declare health as a `[SyncVar]` on a `NetworkBehaviour`. Dynamic objects commonly use registered prefabs. Custom spawn functions are also supported. |
| Who decides when to receive and send? | The host calls `TickIncoming()` and `TickOutgoing()` explicitly. Combat resolution can run between the two calls. | Mirror installs its network updates into Unity's `PlayerLoop`, so the Unity loop drives receiving and sending by default. |
| How do I share a tactical target with teammates? | Put the target on a child Ghost and filter connections with `visibleTo`. The child inherits the parent's visibility and can narrow it further. | Interest Management determines the observers for each `NetworkIdentity`. Use a built-in team or distance policy, or implement a custom policy. |

In the potion example, the client sends a purchase request. The server checks inventory ownership and the available balance, then deducts coins and adds a potion. When changing the buy button, you can give a coding agent just the client implementation and the shared message definition. Purchase validation and inventory updates live in a separate server file. [Client purchase request](Assets/MiniNet/Examples/Inventory.Client.cs) · [Server purchase handler](Assets/MiniNet/Examples/Inventory.Server.cs)

MiniNet fits a workflow where a developer or coding agent defines the network model in C# and tests a round trip in a standalone .NET process. Mirror fits projects that already organize gameplay around Unity scenes, prefabs, and components. [Mirror custom spawn functions](https://mirror-networking.gitbook.io/docs/manual/guides/gameobjects/custom-spawnfunctions) · [Mirror interest management](https://mirror-networking.gitbook.io/docs/manual/interest-management)
